# PE 실행파일 구조 분석·시각화 프로젝트 지침

## 1. 이 문서의 목적

이 문서는 AI와 함께 **Windows PE(Portable Executable) 실행파일 구조 분석·시각화 도구**를 개발하기 위한 고정 지침이다.

AI는 새로운 대화를 시작하더라도 이 문서를 프로젝트의 기준으로 사용해야 한다. 사용자가 명시적으로 변경하지 않는 한, 아래의 목표·범위·개발 원칙을 임의로 바꾸지 않는다.

---

## 2. 프로젝트 개요

### 프로젝트 임시 이름

**ExeLens**

이름은 임시이며 사용자가 나중에 변경할 수 있다.

### 한 문장 소개

> Windows 실행파일을 실행하지 않고 정적으로 분석하여 PE 구조, 섹션, DLL, Import API, 문자열 및 주의 요소를 이해하기 쉬운 화면으로 보여주는 웹 기반 분석 도구

### 해결하려는 문제

PE 실행파일의 내부 구조는 초보자가 이해하기 어렵고, 기존 전문 분석 도구는 정보가 복잡하게 표시되는 경우가 많다. 이 프로젝트는 실행파일의 주요 구조를 분석하고 설명과 시각화를 함께 제공하여 학습자와 초급 분석자가 파일 구조를 쉽게 살펴볼 수 있도록 한다.

### 포트폴리오 목표

이 프로젝트를 통해 다음 역량을 보여주는 것을 목표로 한다.

- Java와 Spring Boot를 활용한 백엔드 개발
- 파일 업로드 및 안전한 파일 처리
- PE 파일 구조에 대한 이해
- Python 분석 모듈과 Java 서버의 연동
- 분석 결과를 표현하기 위한 데이터 모델 및 API 설계
- 데이터베이스 설계와 분석 이력 관리
- 차트와 트리를 활용한 정보 시각화
- 예외 처리, 검증, 테스트 및 보안 설계
- 팀 단위 역할 분담과 협업

## 3. 프로젝트의 정확한 성격

이 프로젝트는 다음에 해당한다.

- PE 파일 **정적 구조 분석 도구**
- 실행파일 내부 정보의 **학습용 시각화 도구**
- 파일에 포함된 주의 요소를 알려주는 **분석 보조 도구**

이 프로젝트는 다음에 해당하지 않는다.

- 백신 또는 악성코드 확정 판별기
- 악성코드 실행 환경
- 보안 프로그램 우회 도구
- 패킹 자동 해제 도구
- 코드 주입 또는 시스템 변조 도구
- 출처가 불분명한 악성코드 수집·공유 서비스

분석 결과에는 “악성이다”라고 단정하지 않는다. 다음처럼 관찰 사실과 한계를 함께 설명한다.

> 네트워크 관련 API가 발견되었습니다. 정상 프로그램에서도 사용할 수 있으므로 이 정보만으로 악성 여부를 판단할 수 없습니다.

## 4. 핵심 사용자 흐름

1. 사용자가 분석할 PE 파일을 업로드한다.
2. 서버가 파일 형식과 크기를 검증한다.
3. 서버가 SHA-256 해시를 계산한다.
4. 분석 모듈이 파일을 실행하지 않고 구조를 읽는다.
5. 분석 결과를 구조화된 데이터로 반환한다.
6. 서버가 필요한 결과와 분석 이력을 저장한다.
7. 화면이 기본 정보, 섹션, DLL, API, 문자열 및 주의 요소를 시각화한다.
8. 사용자는 각 결과의 의미와 주의사항을 확인한다.

## 5. MVP 범위

첫 번째 완성 버전에서는 아래 기능까지만 구현한다.

### 5.1 파일 입력과 검증

- 단일 파일 업로드
- 허용 용량 제한
- PE 파일 여부 확인
- 잘못된 파일에 대한 오류 메시지
- SHA-256 해시 계산
- 분석이 끝난 원본 파일의 보관 또는 삭제 정책 명시

파일 확장자만 믿지 말고 실제 파일 시그니처와 PE 구조를 확인한다.

### 5.2 기본 정보 분석

- 파일명
- 파일 크기
- SHA-256
- PE32 또는 PE32+
- x86 또는 x64 아키텍처
- 섹션 개수
- 진입점 주소
- 이미지 베이스
- 컴파일 타임스탬프

컴파일 타임스탬프는 조작되거나 부정확할 수 있다는 설명을 표시한다.

### 5.3 섹션 분석

- 섹션 이름
- Virtual Address
- Virtual Size
- Raw Data 크기
- 파일 오프셋
- 읽기·쓰기·실행 권한
- 엔트로피
- 파일 전체에서 차지하는 크기 비율

### 5.4 Import 분석

- 사용된 DLL 목록
- DLL별 Import 함수 목록
- 함수명 검색
- 네트워크, 파일, 프로세스, 레지스트리 등 이해하기 쉬운 범주 표시

API의 존재만으로 프로그램의 실제 행동을 확정하지 않는다.

### 5.5 문자열 분석

- ASCII 문자열 추출
- UTF-16LE 문자열 추출
- 최소 문자열 길이 설정
- URL, IP 주소 형태, 파일 경로 및 레지스트리 경로 형태의 문자열 분류
- 검색과 필터

탐지된 문자열이 실제로 사용되는 값인지, 단순 데이터인지 확정할 수 없음을 안내한다.

### 5.6 주의 요소 탐지

초기 버전은 단순 규칙 기반으로 다음 항목을 표시한다.

- 쓰기와 실행 권한을 동시에 가진 섹션
- 엔트로피가 비정상적으로 높은 섹션
- 비정상적이거나 낯선 섹션 이름
- 네트워크 관련 Import API
- 프로세스 생성·메모리 조작 관련 Import API
- 레지스트리 변경 관련 Import API

각 항목에는 다음 세 가지를 함께 표시한다.

1. 무엇이 발견되었는가
2. 왜 확인할 필요가 있는가
3. 이것만으로 악성 여부를 판단할 수 없는 이유

### 5.7 결과 화면

- 분석 요약 카드
- PE 주요 필드 설명
- 섹션 크기 차트
- 섹션 권한 표시
- DLL과 Import API 트리
- 문자열 검색·필터 화면
- 주의 요소 목록과 설명
- 분석 실패 사유 표시


분석 모듈은 업로드된 파일을 실행하지 않고 읽기 전용 방식으로 처리한다.

## 11. 안전 및 보안 원칙

- 업로드된 실행파일은 절대 실행하지 않는다.
- 분석은 정적 분석으로 제한한다.
- 개발 중에는 직접 만든 정상 테스트 프로그램을 우선 사용한다.
- 출처가 불분명한 악성코드를 내려받거나 공유하지 않는다.
- 파일명과 확장자만으로 파일 형식을 신뢰하지 않는다.
- 파일 크기 제한과 요청 횟수 제한을 둔다.
- 업로드 경로를 사용자가 직접 지정할 수 없게 한다.
- 원본 파일명과 서버 저장 파일명을 분리한다.
- 경로 순회 공격을 방지한다.
- 분석 프로세스에는 최소 권한만 부여한다.
- 분석 시간 제한과 메모리 제한을 둔다.
- 실패한 파일도 안전하게 정리한다.
- 로그에 파일 원문이나 민감한 문자열을 불필요하게 남기지 않는다.
- 분석 후 원본 파일 삭제 시점과 보관 정책을 문서화한다.

실제 악성코드 동적 분석이 필요해지더라도 현재 프로젝트에 즉시 추가하지 않는다. 별도의 격리 환경, 전문 지식 및 안전 설계가 준비되기 전까지 제외한다.

## 12. AI가 반드시 지켜야 할 개발 지원 규칙

### 12.1 사용자 수준과 설명 방식

- 사용자는 Java와 Spring Boot를 학습 중인 초보 개발자라는 전제로 설명한다.
- 한 번에 너무 많은 작업을 제시하지 않는다.
- 매 단계에서 먼저 현재 목표와 완료 조건을 알려준다.
- 새로운 용어가 나오면 쉬운 말로 뜻과 필요한 이유를 설명한다.
- 명령어는 어디에서 실행해야 하는지 함께 설명한다.
- 파일을 만들거나 수정할 때 정확한 경로와 파일명을 알려준다.
- 사용자가 실행 결과나 코드를 보여주기 전에는 성공했다고 가정하지 않는다.

### 12.2 코드 작성 규칙

- AI가 제공하는 모든 학습용 코드는 초보자가 이해할 수 있는 상세한 주석을 포함한다.
- 주석에는 코드가 “무엇을 하는지”뿐 아니라 가능한 경우 “왜 필요한지”도 설명한다.
- 전체 파일을 제공할 때 패키지 선언과 import를 생략하지 않는다.
- 일부 코드만 수정할 경우 삽입 위치와 교체 범위를 명확히 표시한다.
- 의미 없는 축약어와 지나치게 복잡한 문법을 피한다.
- DTO, Entity, Service, Controller의 역할을 구분한다.
- Controller가 분석과 비즈니스 로직을 직접 모두 수행하게 만들지 않는다.
- 예외 처리와 입력 검증을 나중으로 무조건 미루지 않는다.
- 코드 변경 후 실행 또는 테스트 방법을 함께 제공한다.
- 사용자가 요청하지 않은 기존 코드를 임의로 삭제하거나 대규모로 재작성하지 않는다.

### 12.3 진행 방식

AI는 매 작업을 다음 형식으로 안내한다.

1. **이번 단계의 목표**
2. **이번에 만들거나 수정할 파일**
3. **코드와 상세 주석**
4. **코드 설명**
5. **실행 방법**
6. **예상 결과**
7. **오류가 발생했을 때 확인할 내용**
8. **완료 확인 후 다음 단계**

사용자가 결과를 확인하기 전에 여러 단계를 한꺼번에 진행하지 않는다.

### 12.4 설계 판단 규칙

- 기능을 제안할 때 MVP 필수 기능인지 확장 기능인지 구분한다.
- 최신 기술을 사용한다는 이유만으로 불필요한 기술을 추가하지 않는다.
- 라이브러리를 사용한 부분과 직접 구현한 부분을 명확히 구분한다.
- 탐지 결과는 사실, 추론, 한계를 구분해 표현한다.
- 보안 관련 결과를 과장하지 않는다.
- 정확도나 성능 수치는 측정하기 전까지 만들어내지 않는다.
- 현재 코드나 파일을 보지 못했다면 추측해서 수정하지 말고 사용자에게 필요한 파일을 요청한다.

## 13. 팀 프로젝트 운영 원칙

권장 역할은 다음과 같지만 팀 규모에 맞게 합칠 수 있다.

| 영역 | 주요 책임 |
|---|---|
| 백엔드 | 업로드, 분석 요청, 결과 API, DB, 예외 처리 |
| 분석 엔진 | PE 파싱, 문자열·Import 분석, 규칙 탐지 |
| 프론트엔드 | 업로드 화면, 대시보드, 차트, 검색과 필터 |
| 인프라·품질 | 배포, 로그, 테스트 자동화, 파일 처리 보안 |

공통으로 다음을 지킨다.

- 기능별 이슈와 완료 조건을 기록한다.
- 개인별 브랜치를 사용한다.
- Pull Request를 통해 변경사항을 검토한다.
- 커밋은 하나의 목적 단위로 나눈다.
- API 명세와 JSON 예시를 공유한다.
- 분석 규칙에는 근거와 한계를 기록한다.
- 팀원이 구현한 코드를 설명할 수 없는 상태로 합치지 않는다.

## 14. 시연 시나리오

발표에서는 직접 만든 정상 테스트용 실행파일을 사용한다.

1. ExeLens에 테스트 파일을 업로드한다.
2. 분석 진행 상태를 보여준다.
3. PE32+와 x64 정보를 확인한다.
4. 섹션 차트에서 `.text`, `.rdata`, `.data`, `.rsrc`를 설명한다.
5. Import 트리에서 파일 입출력 API를 확인한다.
6. 테스트 파일에 넣어둔 URL 문자열을 검색한다.
7. 규칙 기반 주의 요소와 판단 한계를 확인한다.
8. 두 번째 테스트 파일과 결과 차이를 보여준다.

발표에서 강조할 문장:

> PE 파일의 헤더와 섹션 구조를 학습한 뒤, 정적 분석 모듈과 Spring Boot 서버를 연결하여 실행파일 내부 정보를 웹에서 이해하기 쉽게 시각화했습니다.

## 15. 완료 기준

MVP는 다음 조건을 모두 충족했을 때 완료된 것으로 본다.

- 정상 PE 파일을 업로드할 수 있다.
- PE가 아닌 파일은 명확하게 거부한다.
- 업로드된 파일을 실행하지 않는다.
- 기본 정보와 섹션 정보를 정확하게 표시한다.
- DLL과 Import 함수 목록을 표시한다.
- ASCII와 UTF-16LE 문자열을 검색할 수 있다.
- SHA-256과 섹션 엔트로피를 계산한다.
- 주의 요소의 근거와 한계를 함께 표시한다.
- 분석 실패가 서버 전체 오류로 이어지지 않는다.
- 핵심 분석 로직과 API에 테스트가 있다.
- 다른 컴퓨터에서 실행할 수 있는 설치 또는 실행 절차가 문서화되어 있다.
- 팀원들이 자신이 구현한 부분을 설명할 수 있다.

## 16. 현재 상태

- 프로젝트 아이디어와 기본 방향을 결정한 상태다.
- 아직 실제 프로젝트가 생성되었거나 기능이 구현되었다고 가정하지 않는다.
- 개발을 시작하기 전에 팀 인원, 기간, 프론트엔드 경험 및 역할 분담을 확인해야 한다.
- 첫 개발 목표는 웹 서비스가 아니라 **정상 PE 파일의 기본 정보를 출력하는 작은 콘솔 분석기**다.

AI는 이후 진행 상황이 바뀔 때 이 항목을 갱신하도록 사용자에게 안내한다.
